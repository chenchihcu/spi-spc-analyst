# RFC-SPI-COORD-20261023：受控座標檔與量測匯入

狀態：產品規則已確認；本地實作與驗證進行中。正式環境 migration、資料回填與部署均須另外驗收。

## 不變的業務身分

- `rev` 是正式料號版次，不由上傳次序或檔名推定。登錄者選擇料號、版次、面別與 `mm`／`mil`／`inch`。
- `(part, rev, side)` 唯一占用受控座標內容。雙面檔占用 TOP、BOT 兩面；封存仍占用該版範圍。相同 SHA-256 與設定重傳沿用紀錄；不同內容須新正式版次。
- 原始座標與量測檔以 R2 `records/{id}` 保存 gzip；D1 `records` 保存來源 SHA-256、單位、解析版本與稽核。元件中心座標只供元件定位，無實際焊墊座標時不推估。
- 空白座標列忽略；其他列缺位號、X、Y 或有限數值時整檔拒絕。同面完整位號重複才顯示「上傳失敗：重複位號」；跨面重複允許。

## 匯入及判定

- 正式量測要登入並選擇有效受控座標。製令工單或量測日期至少填一項；批號、廠商工單、外包工單選填。日期是使用者提供的 `YYYY-MM-DD`，與上傳時間分開。
- 立榮／振順豐橫排格式的 `U1_1` 對應 `U1`；`PAD ID` 保持焊墊編號。原始 Component ID 和轉換後位號都保存。通用格式完整位號精確比對，不任意去掉尾碼。
- 座標有而量測無不阻擋。量測位號在同面座標找不到時列出全部位號，由使用者確認後保留在非位置統計；另一面找到亦不借用座標。重複量測點拒絕套用。
- 相同料號、版次、面別與原始檔 SHA-256 不新增量測，開啟既有紀錄並顯示中繼資料差異。不同檔案若同工單或同日期，進入 `pending_review`，不納入預設分析。管理者判為新一批後轉 `active`；修正既有時舊紀錄轉 `superseded`，兩份原檔與歷史保留。
- 所有登入管理者可跨上傳者管理。初始管理者由 Worker 執行環境中的 `INITIAL_ADMIN_USER` 指定既有登入帳號，帳號名稱不存入 Git；持久標記只執行一次，最後一位可登入管理者不得撤權。

## API 與資料相容

- `GET /api/records` 支援版次、工單、日期、狀態與游標分頁；座標查詢只回有效受控版本。`POST /api/records` 於伺服器解壓、計算 SHA-256、驗證內容與引用，回應 `201`／`202`／可識別的 `409`。`PATCH /api/records` 用於封存、管理中繼資料及判定關係；`GET/PATCH /api/admin/users` 管理角色。
- 新資料用 `server_verified`，舊資料保留 `legacy` 標記。舊雲端座標須重新讀取原檔、確認設定並驗證，才可納入受控選單；不得自動覆寫或刪除衝突版本。舊本機 IndexedDB 只供查看，新正式匯入不回退本機寫入。
- 目前受控上傳介面僅收 CSV；舊紀錄的 XLSX 仍可讀取作歷史檢視。正式 XLSX 上傳需有可在伺服器獨立解析與驗證原檔的實作，不能依賴瀏覽器傳來的轉換結果。
- 本次 migration 是加欄與新表；保留既有 `records`、`place_id`、稽核、快照及原檔。歷史量測依當時引用讀取，不自動套用目前座標。

## 上線前的停止條件

1. 在資料副本演練 migration，備份 D1 與相關 R2 對應，盤點舊座標單位及同版多檔衝突。不能以檔名或上傳時間補填正式版次。
2. 以既有可登入帳號設定 `INITIAL_ADMIN_USER`；檢查服務端角色與最後管理者保護。
3. 在實際 Cloudflare 環境驗證檔案保存、讀回、權限、並行上傳與修正，以及 Workers 資源限制。測試環境通過才可規劃正式資料與發布。
4. 若需復原，停止新匯入寫入並保留新資料；不可切回會忽略 `pending_review` 的舊程式繼續寫入。

參考樣本：`X3000 V5座標檔.csv` 和 `301-000100124 TOP 量測紀錄.csv`。正式料號與版次需由登錄者確認；樣本檔名不作身分證據。
