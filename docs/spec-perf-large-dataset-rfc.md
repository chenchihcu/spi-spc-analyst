# SPI·SPC 大檔效能技術規格書 (RFC)
**文件編號**：RFC-SPI-2026-003
**版本**：v1.0（已實作於 v9.13.0）
**日期**：2026-10-22
**狀態**：已實作，待審查 (Implemented / For Review)
**審查對象**：SMT 品質工程師 (QE)、製程工程師 (PE)、前端維護者

---

## 1. 問題陳述與目標

### 1.1 背景
使用者匯入約 47,660 筆 SPI 資料（少板多焊墊，約 24 板 × 2,000 焊墊）後，畫面停在「正在偵測問題（47,660 筆，背景計算）…」很久；之後切換量測項目、管制圖、群組或分頁時，**每張圖表、每項分析都要等數秒**。

### 1.2 根因（實測，非推測）

| # | 根因 | 證據 |
|---|---|---|
| **R0** | **問題偵測（背景執行緒）中的 `grpMed`：每張「系統性問題」卡都對每個元件群組重掃全部資料，成本為 O(卡片數 × 群組數 × 筆數)。無封裝欄的機台格式（例如 PHME）以位號為群組，群組數上百時偵測幾乎不會結束** | 48,000 筆、425 群組：舊版 `detectIssues` 52.7 s；只改 `grpMed` 降到 2.0 s；再加上佐證比對記憶化為 1.4 s（407 項問題，結果相同） |
| R1 | `recompute()`（21 處呼叫）每次都在**主執行緒**重跑完整 `analyze()`，包含與所選管制圖、焊墊無關的非常態能力擬合、停機衰減、印刷機補償、空間自相關 | Node 47k 筆：每次 550–650 ms；瀏覽器：切換管制圖／量測項目各阻塞 3.4–4.2 s |
| R2 | 問題很多時（無封裝欄時以位號為群組 → 數百群組 → 上千項問題），問題頁一次畫出全部卡片（每張含兩張 SVG） | 2,423 項問題：問題頁渲染 55 s；背景結果回來後畫面再凍結約 28 s |
| R3 | 問題地圖、進階分析散佈圖對每個群組重掃全部問題／焊墊（O(群組 × 問題)） | 425 群組 × 2,423 問題 |
| R4 | 統計清單 `buildStatsData`、`passFailMatrix`、`dfmTable` 每次進分頁都重算全部資料 | 統計頁每次 2.3 s（瀏覽器） |
| R5 | 偵測在 `analyze()` 之後才送出；`goto()`／`goPad()`／匯入／分享連結會重畫兩次 | 程式碼路徑追查 |
| R6 | 同一份資料重新開啟時，偵測一律重算 | 無持久快取 |

群組少（4 群組）的資料，`detectIssues` 在 Node 約 1.3–2.2 s，熱點平均分散在數十行；以選擇法取代排序求中位數等逐行微調實測只快不到 10%，為保持程式簡潔已撤回（見 §6）。

### 1.3 目標
1. 切換管制圖、焊墊、看過的量測項目 ≤ 80 ms（Node 核心計算），瀏覽器內主執行緒不再出現秒級凍結。
2. 問題頁在上千項問題時仍可在 1 s 內畫出。
3. 同一份資料重新開啟時，偵測結果直接取用。
4. **統計結果逐位元相同**：golden、verdict-sim 與既有測試期望值一律不改。

### 1.4 非目標
- 不改任何統計公式、門檻、抽樣策略或問題排序。
- 不改回合資料庫（`spi-spc` IndexedDB）結構；`saveRunsSoon` 每次複製所有回合列的成本列為後續（§7）。
- 不把 Chart.js 由「重建」改為「更新」。

## 2. 設計

### 2.1 analyze 分層快取（核心 `<script id="core">`）

```
analyze(st)
 ├─ 寫入 hpct（每次都做，維持既有語意）
 ├─ 量測層 B = LRU(anKey(st)) ?? analyzeBase(st)   ← 8 筆，key 綁在 rows 陣列（WeakMap）
 └─ analyzeView(st, B)                              ← 依管制圖算 series／nel，依焊墊算 imr（便宜）
```

| 層 | 快取 key | 內容 |
|---|---|---|
| 資料層 `clsOf(st)` | rows 陣列 + `clsSig`（specs、specSrc、specsG、stencil、htol、step） | 逐列 `classify` 代碼（唯讀共用） |
| 量測層 `analyzeBase` | 資料層 + metric、group、cusumCenter、sqDir、xrSize、xrMode | byBoard、σ、xs／xr／pc／ewma／cusum、cap、ad、sk、sw、groups、msa、rX／rY、nelX、xv |
| 檢視層 `analyzeView` | 每次重組 | imr、pad、series、nel；回傳的物件欄位順序與內容與舊版完全相同 |
| 延遲欄位 `lazy()` | 讀取時才算並存成一般欄位（可列舉、可覆寫） | `nonNormal`／`cap.nonNormal`（依 capDistMode 記憶）、`pauseDecay`、`printerCorr`、`spatialAutocorr` |

- `crossValidate` 只讀量測層欄位（已核對），每組 B 只算一次。
- 空間自相關先取出量測值（`coordV`），延後計算時不受之後改寫 hpct 影響。
- `analyze` 內兩處 O(n × 群組) 的 `rows.filter(group)` 改用已建好的群組索引（加總順序不變）。

### 2.2 各分頁結果快取
- `buildStatsData`：逐列部分依資料 + `clsSig` 快取，Nelson 部分每次依目前分析結果另加。
- `passFailMatrix`：依資料 + `clsSig` 快取（共用分類快取）。
- `dfmTable`：依資料 + `clsSig` + 開孔設定快取，回傳新陣列。
- 能力頁排序後的量測值：依量測層的列陣列快取（hpct 會被改寫，不快取）。
- 交叉驗證頁的散佈圖改用分類快取；熱圖改用不良焊墊 Set；`Math.min(...大陣列)` 改為 `minMax()` 迴圈（資料更大時展開會堆疊溢位）。

### 2.3 問題偵測背景執行緒
0. **演算法修正（R0，逐位元相同）**：`grpMed` 改為先建群組索引並依量測項目記憶；佐證比對（D-29，問題兩兩比較）中每張卡的涉及板與量測項目改為只算一次。
1. **先送出、再分析**：`recompute()` 先把偵測送進 Worker，再在主執行緒算 `analyze()`，兩者並行。
2. **預熱**：開機後 `requestIdleCallback` 先建立 Worker。
3. **進度**：`detectIssues(st, onStage?)` 新增可選回呼，11 個階段（規格與拼板 → 佐證整理），提示列顯示「3/11：系統性問題…」；回呼不影響結果，回呼丟出錯誤也不中斷偵測。
4. **精簡 payload**：`detState()` 略過 `_rawRows`、`grr`、`ai` 等偵測用不到的大型欄位。
5. **結果持久快取**：獨立的 IndexedDB `spi-spc-cache`（store `det`，與回合資料庫分開，不需升級既有資料庫），最多 10 筆，依時間淘汰。
   - key = 程式版本 + 核心程式指紋 + **資料指紋** + 偵測設定（不含回合編號）。
   - 資料指紋 `rowsFingerprint()`：每列全部欄位（不含衍生的 hpct），兩組 32 位元 FNV；數值以 IEEE-754 位元混入，文字以首次出現序號混入並在最後雜湊全部不重複文字。由 **Worker 計算**（4.8 萬筆約 25 ms），不佔主執行緒。
   - 命中時立即採用並終止正在跑的 Worker（之後再重建）；任何失敗都改回即時計算。
6. **只重畫需要的頁**：背景結果回來時，只有問題、總覽、DFM、報告、比較頁重畫。

### 2.4 背景預算其他量測項目（P3）
偵測完成後，同一個 Worker 依序計算目前群組下其他量測項目的量測層結果：

```
主執行緒                                  Worker
 op:"load" {gen, st}（資料世代改變時才送） ─▶ CUR = {gen, st}
 op:"analyze" {gen, key, set}             ─▶ anWork(st)：寫 hpct → analyzeBase → 打包
 anUnpack(P) → anPutKey(rows, key, B)     ◀─ P（列 → 索引；缺陷列副本的 hpct 一併帶回；
                                              非常態能力原始值；空間自相關先算好）
```

- 結構化複製不保留陣列附加欄位，`ewma.rejected` 等另外帶回再補上。
- 預算結果只放進快取的空位（不擠掉使用者正在看的結果）；資料或設定已改變（key 不符）時直接丟棄。

### 2.5 畫面
- **問題頁分批顯示**：先畫前 150 項，「再顯示 150 項（尚有 N 項未顯示）」按鈕；切換篩選或重新偵測時回到 150。跳到未畫出的問題（佐證連結、從證據頁返回）時自動畫到該卡片；列印時畫出全部卡片並展開，列印後恢復。
- 問題地圖一次走過全部問題分到各板／各群組。
- 進階分析散佈圖依群組先分組一次。
- `holdRender()`：`goto()`、匯入套用、分享連結開啟時，中間的 `recompute()` 不重畫，由最後的 `setTab()` 畫一次；`goPad()` 用 `recompute(true)`。

### 2.6 量測儀表（P0）
- 網址加 `?perf=1`，或 `localStorage.setItem("spi-perf","1")`：主控台以 `console.table` 列出 buildRows、analyze、各分頁 render、detect（背景／快取／同步）、背景預算等耗時，同時寫入 `performance.measure("spi:…")`。預設不輸出。
- `node tools/bench-large.mjs`：三種約 4.7 萬筆形狀的核心計算基準。

## 3. 實測結果

### 3.1 瀏覽器（Claude 桌面版內建瀏覽器，正式建置產物 `dist/index.html`）

## 4. 等價性驗證（統計結果逐位元相同）
- `npm test` 全數通過（276 項），golden、verdict-sim、既有期望值皆未修改。
- `tests/perf-cache.test.mjs`：
  - 快取路徑與全新核心（無任何快取）重算的 `analyze` 結果逐字相同。比對涵蓋範例 A、階梯鋼板、40 板 × 300 焊墊，以及量測項目 × 群組 × 管制圖 × 焊墊 × 分布模型的組合。Set／Map 以型別標籤比對，跨 `vm` 環境也有效。
  - 延遲欄位：讀取前為 getter、讀取後為一般欄位、可列舉、可覆寫，且與 `cap.nonNormal` 為同一份結果。
  - 規格改變會讓快取失效，改回原設定則沿用原結果。
  - `buildStatsData`／`passFailMatrix`／`dfmTable` 快取結果與重算相同；開孔設定改變後 DFM 表會重算。
  - 背景預算：打包 → `structuredClone` → 還原後，`analyze` 結果與同步計算逐字相同（含其他分布模型）。
  - `detectIssues` 進度回呼依序回報 11 個階段且不影響結果。
  - 資料指紋對數值、文字、列順序、筆數、空值改變都敏感，且忽略 hpct。
  - 效能預算：4.7 萬筆時切換管制圖／焊墊／回到看過的量測項目 < 80 ms，統計清單第二次 < 20 ms。
- 前後快照比對（開發期間工具）：7 種資料情境 × 875 個輸出雜湊（analyze 各組合、非常態能力、進階分析、detectIssues、統計清單、合格矩陣、DFM 表）完全相同。

## 5. 相容性與風險

| 風險 | 處置 |
|---|---|
| 快取在資料被就地改寫後失真 | 已核對：列物件建立後只有 hpct 會被改寫，且 hpct 不進快取 key 的資料指紋。hpct 依鋼板設定重算，鋼板設定已在 `clsSig` 內；`analyze` 每次仍先寫 hpct |
| 延遲欄位被當成一般屬性覆寫 | `lazy()` 提供 setter，覆寫後成為一般欄位 |
| 舊版偵測快取在程式更新後誤用 | key 含版本與核心程式指紋 |
| IndexedDB 不可用（私密瀏覽） | 所有快取操作失敗即略過，改回即時計算 |
| 問題頁只畫前 150 項，使用者以為只有 150 項 | 嚴重度標題顯示總數並註明「顯示前 N 項」，下方按鈕顯示剩餘數；篩選列的計數不變 |

## 6. 評估後未採用
- **`med`／`robust`／`isoStat` 改用選擇法（quickselect）**：已證明逐位元相同（2 萬組模糊測試），但 4.7 萬筆只快 5–10%，為保持程式簡潔撤回。
- **問題卡片內容延後到展開時才產生**：會改變「每張卡片都有證據圖與前往按鈕」的既有測試契約，改採分批顯示。

## 7. 後續（不在本次範圍）
1. `saveRunsSoon` 每次存檔都結構化複製所有回合的全部列：需拆分回合資料庫結構（持久化契約變更，需另行核准）。
2. 匯入預覽每次改欄位對應都完整重跑 `buildRows`（4.8 萬筆約 1 s）：可改為抽樣預覽或延遲執行。
3. 進階分析頁在數百群組時，Chart.js 散佈圖的資料集數量（每群組一組）是主要成本，屬視覺設計取捨。
4. 問題數上千時，從偵測第 11 階段「佐證整理」開始到結果送回主執行緒實測約 3 s（含結果回傳與存入快取）；佐證比對為問題兩兩比較，可另行評估索引化。
